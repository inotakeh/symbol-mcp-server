# Symbol MCP Server development brief (v2, revised after a review of current conventions)

Instructions for an agent with no prior knowledge. It is written so that this document alone is enough to start.
Anything unclear must be checked in the references in §12 (the OpenAPI specification, the SDK docs, a live node), not guessed.

> **Changes from v1 (applied on 2026-09-10 after checking the official documentation)**
> - The SDK is **`@modelcontextprotocol/server` 2.0.0** (published 2026-07-27), not the old `@modelcontextprotocol/sdk` (the v1 line). The API is `registerTool` / `serveStdio`, with Zod v4.
> - Tool names are namespaced throughout as `symbol_<resource>_<action>` (following Anthropic's guide to tool design).
> - **Removed every argument with which the model could name an arbitrary URL** (against SSRF, following the MCP security guide). Reference nodes come only from an allowlist in an environment variable.
> - `annotations` (readOnlyHint and the like) and `outputSchema` + `structuredContent` are now required on every tool.
> - Tests use the SDK's official in-process approach (`createMcpHandler` + `Client`).
> - The publishing steps now follow the MCP Registry's actual procedure (`mcpName` / `server.json` / `mcp-publisher`).

## 1. Background and purpose

**Symbol** is a public blockchain (the successor to the old NEM, but a **separate chain** from NEM/XEM). Its native currency is **XYM**. Each node exposes a REST API (usually 3000=http / 3001=https) that can be read without authentication.

What to build: **a server that makes the Symbol REST API usable as MCP (Model Context Protocol) tools**. It has 2 kinds of users.

- **Account holders**: lookups of balances, transactions, mosaics (tokens) and namespaces, fee estimates, address validation
- **Node operators**: node status, sync check, harvesting status, **computing the expiry date of voting keys**

The design comes down to 3 points. Make task-level tools that answer questions instead of mirroring the REST endpoints as they are (§2-2). Guarantee with a regression test that the configured node URL is the one actually used for requests (§7). Include the LICENSE (MIT) in the first commit (§3).

## 2. Design principles (required)

1. **Read-only**. Never create an argument that accepts a private key or mnemonic. Never sign. Never turn `PUT /transactions` (announcing) into a tool.
2. **Each tool answers a question**. Never mirror an endpoint. 22 tools in total (§5; `TOOLS` in `src/server.ts`; the `check` of §13 is a CLI subcommand and does not count as a tool). Follow Anthropic's guide: "consolidate several lower-level operations into a single task-level tool".
3. **The node URL is set only through an environment variable** (`SYMBOL_NODE_URL`). **Tools never take a URL as an argument** (that would be an SSRF path through which the model could point requests at the internal network). At start-up, fetch `/node/info` and detect mainnet/testnet from `networkGenerationHashSeed`. If `SYMBOL_NETWORK` is set and does not match, **start-up fails**. Log the node in use and the network to stderr.
4. **Output is structured and human-readable**. Define an `outputSchema` for every tool, and return **both** `structuredContent` and a `text` block holding its JSON string (a backward-compatibility requirement of the specification; the exception is `output: csv` of `symbol_harvesting_income`, where the text is the CSV body, §5.2). `structuredContent` must always include `summary: string` first (a short summary whose line 1 answers the question; lines such as one per month, one per check that is not ok, or the line with the count of removed characters may be added after it). Amounts are given both with divisibility applied and as the raw integer. Dates and times are ISO 8601 (UTC), plus the local time when `SYMBOL_TIMEZONE` is set. Numeric IDs are resolved to names (e.g. `6BED913FA20223F8` → `symbol.xym`, `16724` → `transfer`).
5. **Never hard-code network constants**. Fetch them from `/network/properties` and cache them per process. Known values are used only as expected values in tests (exception: the generationHashSeed table in §4).
6. **Return errors as `isError: true` results, with a recovery hint in the text** (e.g. "An address is 39 characters of base32. If you passed hex, convert it with symbol_address_parse"). Never return stack traces or raw HTTP responses as they are.
7. **Outbound traffic goes only to `SYMBOL_NODE_URL` and `SYMBOL_REFERENCE_NODES`**. Telemetry is forbidden.
8. **Never trust chain strings**. Transfer messages, metadata values, namespace names and what a node reports about itself (friendlyName, host, the `/node/health` status, the restVersion of `/node/server`, the code of a transaction status) can be written by third parties. In the output, put them in fields whose names show that they are `untrusted` (e.g. `messageText`), and make them 1 line with `sanitizeUntrusted` in `src/domain/sanitize.ts`: tabs and line breaks (TAB, LF, VT, FF, CR, NEL, line separator Zl, paragraph separator Zp) become 1 space (so that the words on either side do not run together); every other control character (Cc), format character (Cf), lone surrogate (Cs) and the tag character block U+E0000 to U+E007F (unassigned code points included) is removed; runs of spaces (U+0020) are collapsed into 1; the spaces at both ends are trimmed; and the length is capped (a surrogate pair is never split). Ideographic spaces and NBSP are kept, not collapsed. Variation selectors are kept. The status is also judged (whether it is `up`) on the cleaned value, so that what is shown and what is judged agree. Typed fields of transaction details take only values of the OpenAPI shape (MetadataKey and RestrictionKeyHex are 16-character hex, VotingKey is 64 characters); anything else falls back to the cleaned `other`. When an error message quotes a value from the node, that value also goes through the same removal and cap.
   - **Count of removed characters (`invisibleCharactersRemoved`)**: the 17 tools that put third-party strings in their output (§5 "Common conventions") return how many characters (Cc, Cf, Cs, tag characters) were removed in that call. Line breaks and tabs turned into spaces, spaces collapsed or trimmed, and length truncation are not counted (removal comes before truncation, so invisible characters in the part cut off at the cap are counted). Strings from the same origin are counted only once in 1 call: each cleaned value carries a key naming its origin (`mosaic-alias:<id>` for the alias of each mosaic, `namespace:<id>` for each level of a namespace), so that a currency alias cached per process, a parent namespace shared by 2 names, and the same name fetched 2 times in 1 call are also counted only 1 time. Strings that do not appear in the output are not counted (the currency label of a transaction whose fee is not shown, a namespace name not used for a recipient). An alias or name with nothing left after removal is treated as absent (the mosaic id or the name the caller wrote is shown instead; the same goes for a name with a missing level), and the removed characters are counted. priceSource and priceAsOf likewise count as not given when nothing is left. When the count is 1 or more, 1 line "Removed N invisible characters …" is added at the end of the summary (it does not start with `- `; line 1 does not change).
   - **Removal goes through 1 path**: when a tool definition has `untrustedText: true`, `defineTool` creates an `UntrustedText` (removal and counting) for each call and passes it to `run(ctx, input, text)`, adds `invisibleCharactersRemoved` at the end of the outputSchema, and adds the field and the summary line to the result (the same through MCP and in CLI check). Third-party strings must always reach the output through `text.clean` (removal on the spot) or `text.use` (a value already cleaned by `cleanUntrusted`; the currency alias, `resolveMosaicAliases` and `resolveNamespaceNames` return cleaned values with their counts of removed characters, so at the type level too they do not become strings without going through `text`). Error messages, logs and the CLI, which need not be counted, use `sanitizeUntrusted`. The types cannot catch a cleaned value (an object) put straight into a template string, so the cross-tool tests also check that no "[object Object]" appears.
   - **Removal is not moved into the response schemas** (considered in 2026-09): a zod transform can return only a string and cannot carry the count of removed characters (returning an object changes the type for every consumer, and a global tally would mix the counts of calls running at the same time) / a currency alias cached per process is parsed only once, when it is fetched / message and metadata values are decoded after their hex is parsed, and priceSource is the caller's input, which does not pass through a schema. The schemas handle only shape and length caps; removal by a zod transform in transaction details was dropped as well, so that everything goes through the 1 path above.
9. **Local state file** (added in 0.3.0). Only `symbol_harvester_watch` writes to disk, and only to `harvesters-<first 16 hex of nodePublicKey>.json` under `SYMBOL_STATE_DIR` (optional; an absolute path). The content is only the public keys, heights and times of the unlocked harvesters, with no secrets. Deleting it does not affect operation (the next call becomes the baseline). When the variable is unset, nothing is written and only the current list is returned, marked "no comparison possible". Only 1 file, `src/state/snapshotfile.ts`, imports fs (auditable with `grep -rl node:fs src/`). Calling it several times on the same day stores that many snapshots, bounded to the newest 60. `readOnlyHint: true` stays (the model can choose neither the path nor the content; all it can write is "append today's list").

**Notes on using SDK v2**
- v2 was published only recently. If a fatal bug is hit, falling back to `@modelcontextprotocol/sdk` 1.x (the `server.tool()` API) is an option, but even then, keep the design in this document. v1→v2 can be migrated mechanically with `npx @modelcontextprotocol/codemod@latest v1-to-v2 .`.
- By default, `serveStdio` serves both protocol eras, "2025 (the `initialize` handshake)" and "2026-07-28", from the same factory. **Keep the default** (some hosts are still on the older era).
- The 2026-07-28 specification deprecates the Roots / Sampling / Logging features. **Write logs to stderr, not through the MCP logging feature**. `console.log` is forbidden (stdout is the JSON-RPC channel, and 1 line breaks it).

### 3.1 Server instructions and Prompts (added in 0.2.0)

**instructions**: put in the initialize result with `new McpServer(info, { instructions })` (SDK v2 `ServerOptions.instructions`; the npm package does not include `docs/`, so this was verified in `dist/*.d.mts`). The text is `SERVER_INSTRUCTIONS` in `src/instructions.ts` (English, 150 words at most; `test/unit/instructions.test.ts` checks the word count). It says only what the tool descriptions cannot convey: read-only, accepts no private key, signs and announces nothing / an account is a 39-character base32 address, a 64-character hex public key or a namespace name / harvest rewards are receipts, so use `symbol_harvesting_income` (not `symbol_transaction_search`; the arguments for monthly totals and CSV) / to value holdings in a currency, obtain the unit price first and pass it to `symbol_holdings_value`, never computing balance × unit price yourself (added in 0.7.0) / a list, in 1 sentence, pairing each question that is easy to mix up with its tool (after `Route by question:`, "question, tool" pairs separated by `;`: rank by holdings, voting key expiry, finalization votes signed, delegated harvesting not working, delegators gained or lost, health of the node's services, sync, version behind, height difference from other nodes, whether a transaction went through or failed) / numbers are computed by the server, so the model does not recompute them. Existing sentences were compressed to fit in 150 words (how tool descriptions are built: §5 "Common conventions"). Clients can read it with `client.getInstructions()` (checked in the tool-layer tests).

**Prompts**: `server.registerPrompt(name, { title, description, argsSchema: z.object(...) }, cb)`. `src/prompts/` has 1 file for 1 prompt, registered in the order of the `PROMPTS` array in `server.ts` (as with tools, only appended, never reordered). The only argument is `account` (a base32 address). The callback runs it through `isValidBase32Address` and makes prompts/get fail when it is invalid. The body is a template in which `{account}` is replaced, and **never contains a real address, host, key, hash or date** (`test/tools/prompts.test.ts` checks with regular expressions both the template before replacement and what remains of the body after replacement once the passed account is taken out).
- `voting_key_renewal_checklist`: `symbol_voting_key_status` (endEpoch, estimated expiry, recommended renewal window, free slots) → `symbol_node_status` (stop if not synced) → `symbol_network_compare` → a human runs the renewal commands → check with `symbol_transaction_status` that the Tx hash the user gives is confirmed → `symbol_voting_key_status` again (the new key is active / future; the expired key was unlinked and its slot freed) → once the new key's startEpoch is finalized, `symbol_finality_participation` (that epoch is `participated` = signed both prevote and precommit; `missed` means the key is registered but the node is not voting with it, so tell the user to check the voting node's key files and sync) → 4 lines: "current key / new key / estimated expiry / open items".
- `monthly_health_check`: `symbol_node_status` → `symbol_node_health` (the verdict and the items at warn or worse; unhealthy goes first) → `symbol_version_drift` (the verdict, the configured node's version, majorityVersion; behind or worse goes first) → `symbol_network_compare` → `symbol_harvester_watch` (mode `compare_and_save`; `current.count` and, from `comparison`, previousCount / previousTakenAt / the numbers added and removed / deltaCount; a negative delta needs attention. When `comparison` is null and the notes say that `SYMBOL_STATE_DIR` is not set, ask the user for the previous value; on the first run, report that a baseline was saved. `symbol_harvesting_status` only when the limits or the key list are asked for) → `symbol_voting_key_status` (a warning goes first when within 30 days) → `symbol_account_get` (balance vs `minVoterBalance`) → `symbol_harvesting_income` (from the 1st to the last day of the previous month, daily; after `totals.xym`, `totals.receipts` and the daily average, report `totals.blocksHarvested` (blocks the account harvested itself) and `totals.blocksBeneficiaryOnly` (blocks of delegators and others) as separate items, stating that the number of beneficiary receipts is not the number of delegators' blocks) → 1 screen in 3 levels: Action required / Attention / Normal.

## 5. Tool specifications

### Common conventions

- **Names**: `symbol_<resource>_<action>` in snake_case (the specification allows the characters `[A-Za-z0-9_.-]`, 1 to 128 characters). Give each tool a display name for humans in `title`.
- **Argument names**: leave no ambiguity (`address` / `publicKey` / `transactionHash`, not `id`). Every argument must have a `.describe()` (the only description the model reads).
- **How a description is built**: sentence 1 starts with an imperative verb and says which question the tool answers (within a group that is easy to mix up, each tool uses a different verb and object, and names no other tool). Sentence 2 points to the other tools of the group ("for …, use X"), and sentence 3 onward gives the details of the output. The groups that are easy to mix up: `symbol_node_status` (sync and identity) / `symbol_node_health` (health of the services) / `symbol_version_drift` (version behind) / `symbol_network_compare` (height difference from other nodes); `symbol_transaction_get` (contents) / `symbol_transaction_status` (whether it went through, and why it failed; a failed Tx is not in the groups that get reads, so get reports not_found); `symbol_harvesting_status` (the node's unlocked list and limits) / `symbol_harvester_watch` (increase or decrease of the list) / `symbol_delegation_diagnose` (whether the delegation of 1 account is active) / `symbol_harvesting_income` (rewards) / `symbol_account_get` (balance, keys, settings). As an exception, `symbol_harvesting_income` keeps "use this tool whenever the user asks about harvesting rewards, harvest income, or earnings for a period" in sentence 1 and "Do not use symbol_transaction_search or a browser for this (harvest rewards are receipts, not transactions)" in sentence 2 (sentences that fixed real harm: Claude Desktop overlooked this tool and tried to answer with a browser; if they are removed, use other wording of the same strength). Sentence 1 also becomes the tools declaration in the .mcpb manifest (§14). The groups and the tools each description points to are fixed by `test/unit/tool-descriptions.test.ts`.
- **Resolution rules for the account argument** (added in 0.2.0; `resolveAccountInput` in `src/tools/_accounts.ts`; every tool that takes an account goes through it = `symbol_account_get` / `symbol_voting_key_status` / `symbol_harvesting_status` / `symbol_harvesting_income` / `symbol_finality_participation` / `symbol_delegation_diagnose` / `symbol_account_rank` / `symbol_holdings_value` / the `address` of `symbol_transaction_search` / the `value` of `symbol_address_parse`):
  1. Classification order (`classifyAccountId`): 64-character hex public key → 48-character hex address → 39-character base32 address (**only when the checksum verifies**) → namespace name (`[a-z0-9][a-z0-9_-]*`, up to 3 levels joined by `.`, each part 64 characters or fewer; verified in the SDK's `idGenerator.js` and in `maxNameSize` / `maxNamespaceDepth` of `NamespaceNetworkPropertiesDTO`. `classifyAccountId` trims the spaces around the input before checking for any form (`' alice.pay '` is `alice.pay`); apart from that, a name is judged as written and is not lower-cased (`ALICE` and `alice pay` are invalid)) → if none matches, `isError` + a hint (the hint says that a namespace name also works). A lower-case 39-character input whose checksum fails falls through to the namespace check (so that a valid name of exactly 39 characters is not misjudged as "an invalid address"). An upper-case typo fails both rules and stays invalid. A lower-case 64-character hex string is also a legal name, but the public key wins first.
  2. Name → namespaceId is computed by `src/domain/namespace.ts` (the same SHA3 path as `symbol_namespace_get`). `GET /namespaces/{id}` goes through the per-process cache of `AppContext.getNamespaceInfo`. The TTL is `chain.blockGenerationTargetTime` (1 block; aliases can change, so do not make it longer; never hard-code the constant).
  3. Judgment (verified with the OpenAPI `AliasDTO` / `AliasTypeEnum` / `NamespaceMetaDTO`): 404 → "does not exist (never registered, or expired or deleted)" / `meta.active === false` → "expired" / `alias.type === 1` (mosaic) → "an alias of a mosaic (not an address)" / `alias.type !== 2` or no `address` → "has no address alias". All of them are `isError` + a hint. When `type === 2`, `alias.address` (hex) is converted to base32 and processing continues. When there is no account at the resolved address, `fetchAccount` reports "no account at the alias target".
  4. Output: the common optional field `accountResolution: nullable({ input, namespace, namespaceId, address })` (null when an address or public key is given directly; `symbol_harvesting_status` also gives null when no account is given). Line 1 of the summary starts with `alice → NCV5… (full address). ` (`withResolutionPrefix`). The name is treated like any chain string and goes through `sanitizeUntrusted`. `symbol_address_parse` returns the resolved address and the namespaceId with `kind: 'namespace'`, and its description states that only this form contacts the node.
  5. Reverse lookup (address → name) is not done in this version. A future candidate: adding `accountNames` through `POST /namespaces/account/names`.
  - Tests: unit (the classification order; negative cases for the name rule: upper case, a space, 4 levels, an empty part, a leading `-`, 65 characters, the 39-character fall-through), tool-layer `test/tools/account_resolution.test.ts` (synthetic namespace `fixture-alias` → a synthetic main account; given by name and given directly, the body is the same and only `accountResolution` differs / the 4 kinds of errors / expired / no account at the alias target / TTL cache / `symbol_address_parse` / no fetch to anything but `SYMBOL_NODE_URL`), and the smoke calls on both eras in `EXTRA_SMOKE_CALLS` (kept apart because `SMOKE_CALLS` has an assert that is 1:1 with the tools).
- **annotations**: state `{ readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: true }` explicitly on every tool (openWorld is true because the tools talk to external nodes).
  The defaults in the specification (verified in `ToolAnnotations` of `schema/2025-11-25` and `schema/2026-07-28`; note that the defaults are written in the description text as "Default: …", not as a JSON Schema `default` key):
  `readOnlyHint` = **false**, `destructiveHint` = **true**, `idempotentHint` = **false**, `openWorldHint` = **true**.
  That is, **a tool that states nothing is treated as "a destructive tool that may change state"**, so a read-only server must state `readOnlyHint: true` explicitly. `destructiveHint` and `idempotentHint` mean something only when `readOnlyHint == false` (stating them is harmless).
- **Fix the registration order**: the 2026-07-28 specification added that `tools/list` returns its tools in a deterministic order (SHOULD), for client-side caching and prompt caching. Define the tools in an array and always call `registerTool` in the same order. The same specification's `ttlMs` / `cacheScope` (SEP-2549) are declared with `ServerOptions.cacheHints` only for `tools/list` and `prompts/list`, which are static and do not depend on authorization (`ttlMs` 24 hours = the client-side maximum `MAX_CACHE_TTL_MS`, `cacheScope: 'public'`; `LIST_CACHE_HINTS` in `src/server.ts`). Results of `tools/call` and the like keep the SDK defaults (0 / private). Responses of the 2025 era carry none of these fields (both are checked in tool-layer tests: `test/tools/era_2026.test.ts` and `server.test.ts`).
- **Output**: define an `outputSchema` (zod) and return both `structuredContent` and `content: [{type:'text', text: JSON.stringify(structuredContent)}]`. The first field is `summary`. The tools that put third-party strings in their output (the 17 tools `symbol_network_info`, `symbol_node_status`, `symbol_account_get`, `symbol_voting_key_status`, `symbol_transaction_get`, `symbol_transaction_search`, `symbol_mosaic_get`, `symbol_namespace_get`, `symbol_fee_estimate`, `symbol_harvesting_status`, `symbol_harvesting_income`, `symbol_transaction_status`, `symbol_delegation_diagnose`, `symbol_node_health`, `symbol_version_drift`, `symbol_account_rank` and `symbol_holdings_value`) set `untrustedText: true`, and their last field is `invisibleCharactersRemoved` (§2-8; `defineTool` adds it). The other 5 tools (`symbol_address_parse`, `symbol_finality_participation`, `symbol_time_convert`, `symbol_network_compare`, `symbol_harvester_watch`) output no string that third parties can write freely. When adding a tool, set it if the tool outputs such strings and leave it unset if not (the cross-tool tests check both directions).
- **When adding a field to an outputSchema, raise the minor version and say so in the release notes**: the outputSchema the SDK publishes has `additionalProperties: false`, and the client SDK validates structuredContent against the outputSchema in its cached `tools/list` (`callTool` in `@modelcontextprotocol/client`). A client that keeps the `tools/list` from before the update (the 2026 era allows caching `tools/list` for up to 24 hours) can reject a result that contains the new field with a validation error. Making the new field optional does not prevent this, because the old schema rejects extra fields. Write "restart the MCP host after updating" in the release notes.
- **Large outputs**: add `format: z.enum(['concise','detailed']).default('concise')` and `pageSize` (default 10, maximum 100); when truncating, set `truncated: true` and write in `summary` how to get the next part.
- **Errors**: `{ content:[{type:'text', text:'<what is wrong>. <how to fix it>'}], isError: true }`. Distinguish an unreachable node, a timeout, a 404, a network mismatch and invalid input.

### 5.1 For account holders

**`symbol_network_info`** — no arguments (`inputSchema` is omitted).
Network name, identifier and generationHashSeed, current height, finalized height/finalization epoch, `blockGenerationTargetTime`, the mosaicId and divisibility of XYM, `epochAdjustment`, and the current fee multipliers (min/average/median/highest of `/network/fees/transaction`).

**`symbol_account_get`** — `account` (a base32 address, a 48-character hex address, a 64-character hex public key, or a namespace name with an address alias; the resolution rules in §5 "Common conventions"), `format`.
Address (base32 and hex), public key, every mosaic balance (id, alias name, amount with divisibility applied, raw integer), importance and importanceHeight, `supplementalPublicKeys` (linked / vrf / node / voting[]; voting with start/endEpoch), whether delegated harvesting is set up ("set up" when both linked and vrf exist), and multisig information (unless `/account/{id}/multisig` is a 404). catapult keeps an entry for both the multisig account and its cosignatories, so the two are told apart: 1 or more `cosignatoryAddresses` means a multisig account (summary `multisig M-of-N`), and 1 or more `multisigAddresses` means a cosignatory (`cosignatory of N multisig accounts`; a cosignatory's minApproval and minRemoval are 0) (both, in a multilevel multisig).
Reference: `GET /accounts/{accountId}` (accepts both an address and a publicKey).

**`symbol_transaction_get`** — `transactionHash`.
Type name (from the numeric code to a name; §6), signer address, recipient, mosaics and amounts (names resolved, divisibility applied), message (decoded when plain; when encrypted, stated as "encrypted message"), fee (XYM), height, timestamp (ISO), and for an aggregate a summary list of its inner transactions.
Reference: `GET /transactions/confirmed/{transactionId}`. When it is not found, also tries `/transactions/unconfirmed/{id}` and `/transactions/partial/{id}` and returns the status (confirmed/unconfirmed/partial/not_found).

**`symbol_transaction_status`** (added in 0.2.0; registered at the end of the tool array without changing the existing order) — `transactionHashes` (an array of 64-character hex, 1 to 20 entries; even 1 hash is passed as an array. An empty array, 21 or more entries, or invalid hex is checked inside `run` and gives `isError` + a hint. Duplicates are merged into 1, and the order is the input order).
The question it answers: "What state is the transaction with this hash in now (confirmed / unconfirmed / waiting for cosignatures / failed)?". For checking right after the link of a key renewal is announced. For the contents, `symbol_transaction_get`.
Output: `statuses[]` with `{ hash, group: confirmed|unconfirmed|partial|failed|not_found, code, codeMeaning, height, deadline }` for each hash, `counts`, and `note`. When `code` is not `Success`, `codeMeaning` gives its meaning. The table `src/domain/txstatus.ts` is imported mechanically from the `enum` list and the `description` block of the OpenAPI `spec/core/transaction/schemas/TransactionStatusEnum.yml` (`Success` / `Neutral` / `Failure` / `Failure_Hash_Already_Exists`, which have no description, and codes not in the enum get `codeMeaning: null`; nothing is ever filled in from memory). `height` is given only when confirmed; `deadline` is converted to wall-clock time with `epochAdjustment`. In the summary, partial gets "waiting for cosignatures (aggregate bonded, cosignatures missing)". A hash missing from the response, and a 404 for the whole batch, are `not_found` and not `isError`.
Reference: `POST /transactionStatus` (body `{ "hashes": [...] }`, `spec/request_bodies/schemas/transactionHashes.yml`) → `TransactionStatusDTO[]` (`{ group, code?, hash, deadline, height? }`; group / hash / deadline are required; `TransactionGroupEnum` = `unconfirmed | confirmed | partial | failed`). The status is that of the node asked, so the node that received the announcement knows the most (a note in the OpenAPI; also written in `note`).

**`symbol_transaction_search`** — `address` (an address, public key or namespace name; the resolution rules in §5 "Common conventions"; the transactions it takes part in as signer or recipient), `type` (optional; a name or a number), `pageSize` (10 to 100, default 10), `pageNumber` (1 to 10,000, default 1), `order` (desc by default), `format`.
A summary list in the same form as above + paging information (`pagination.nextPageNumber`; when more may follow, the summary gives the next `pageNumber`).
Reference: `GET /transactions/confirmed?address=...&type=...&pageSize=...&pageNumber=...&order=desc`.

**`symbol_mosaic_get`** — `mosaic` (a 16-character hex ID or an alias name such as `symbol.xym`).
ID, alias name, supply, divisibility, flags (supplyMutable / transferable / restrictable / revokable), owner, start height, duration (duration=0 means it never expires).
Reference: `GET /mosaics/{mosaicId}`; names are resolved with `GET /namespaces/{namespaceId}`.

**`symbol_namespace_get`** — `namespace` (a name or a 16-character hex ID).
Owner, kind (root/sub), alias target (address or mosaicId), start/end height and the **estimated end date** (converted as in §6).
Reference: `GET /namespaces/{namespaceId}`.

**`symbol_fee_estimate`** — `transactionSizeBytes` (optional; when not given, the size of a typical transfer transaction is used).
Estimates from the multipliers of `/network/fees/transaction` × the size, converted to XYM, in the tiers `slow` (`minFeeMultiplier`, the minimum this node accepts), `average`, `median` and `fast` (`highestFeeMultiplier`, the highest in recent blocks). Nothing is announced.

**`symbol_address_parse`** — `value` (a base32 address / hex address / public key / namespace name; only a name makes it ask the node; §5 "Common conventions").
Validity, kind, both the base32 and hex forms, the network it belongs to (first character N=mainnet, T=testnet), and for a public key the address derived from it.

**`symbol_time_convert`** — exactly one of `height`, `epoch` or `timestamp` (network timestamp in ms).

### 5.2 For node operators

**`symbol_node_status`** — no arguments (the target is `SYMBOL_NODE_URL`).
friendlyName, host, roles (the bit flags expanded into Peer/API/Voting), version (the 4-byte integer decoded into the form `1.0.3.9`; e.g. 16777993 → `1.0.3.9`), network, the apiNode/db status from `/node/health`, current height/finalized height/finalization epoch, peer count (the number of entries in `/node/peers`), and the **sync check** (the timestamp of the latest block is converted to wall-clock time, and when it is more than 5 minutes away from the current time, `synced: false` with a warning).

**`symbol_voting_key_status`** ← **the most important tool** — `account` (an address, public key or namespace name; the resolution rules in §5 "Common conventions").
- List of registered voting keys: publicKey, startEpoch, endEpoch, status (`expired` / `active` / `future`)
- The current finalization epoch and the current height
- For active keys and keys not started yet (future): remaining epochs, remaining blocks, **remaining days**, the **estimated expiry date** (ISO/UTC + local), and the **recommended renewal window** (7 to 3 days before expiry). A future key also gets its estimated start date (`startsAt`) (an expired key gets none of these)

- Add 1 entry each to `warnings[]` when: there is no active key (with the start epoch of the next key when a future key exists) / an active key expires within 30 days and no future key takes over without a gap (`hasSuccessorKey` in `src/domain/voting.ts`; the same rule as the check of §13) / the balance is below `minVoterBalance` / the free slots are 0
The calculation is in §6.

**`symbol_harvesting_status`** — `account` (optional; an address, public key or namespace name; the resolution rules in §5 "Common conventions").
The number of delegated harvesters unlocked on the node and the list of their public keys (`/node/unlockedaccount`), `minHarvesterBalance` / `maxHarvesterBalance` / `harvestBeneficiaryPercentage`, and, when `account` is given, whether its linked public key is in the unlocked list (= whether it can actually harvest on this node).
- The balance range (`balanceWithinLimits`) is `minHarvesterBalance <= balance <= maxHarvesterBalance` (the balance of harvestingMosaicId; both ends inclusive). The part above the maximum is not cut off; instead, **above the maximum, the account cannot harvest**. catapult's `ImportanceView::canHarvest` (`client/catapult/src/catapult/cache_core/ImportanceView.cpp`) requires an importance other than 0 and a balance within the range, both ends included, and `EligibleHarvesterValidator` rejects the blocks of a harvester that does not meet this with `Failure_Core_Block_Harvester_Ineligible` (test `FailureWhenBalanceIsAboveMaxBalance`). In addition, `UnlockedAccountsUpdater::pruneUnlockedAccounts` of the harvesting extension drops from the node's unlocked list the delegators that do not meet `canHarvest` at the next height. `canHarvestHere` includes this range in its judgment. It is the same rule as `balance_in_range` of `symbol_delegation_diagnose`, and the 2 tools share `classifyHarvesterBalance` (below / within / above) in `src/domain/delegation.ts` (so that they never disagree again). Importance, too, is given from exactly the minimum (catapult `HighValueAccounts.cpp`: `balance >= MinHarvesterBalance`).

**`symbol_network_compare`** — no arguments (the targets are `SYMBOL_REFERENCE_NODES`).

**`symbol_harvesting_income`** (added in 0.2.0; registered at the end of the tool array without changing the existing order) — `account` (an address, public key or namespace name; the resolution rules in §5 "Common conventions"), the period as **exactly one of** `fromDate`/`toDate` (`YYYY-MM-DD`, both ends inclusive; dates in `SYMBOL_TIMEZONE`, or UTC when it is unset) and `fromHeight`/`toHeight` (both, neither, only one of a pair, a reversed range, or a date that does not exist is `isError`), `granularity` (`daily` by default / `monthly` / `receipt`), `format` (the level of detail of the JSON; the limit with `receipt`: 50 for concise / 500 for detailed), `output` (`json` by default / `csv`; the form of the text block, independent of `format`).
- Totals only those HarvestFee (8515; written Harvest_Fee in the OpenAPI `ReceiptTypeEnum`) receipts addressed to the account in the given period that are in the currency mosaic (`currencyMosaicId` of `/network/properties`). Counts and totals are **computed deterministically on the server with BigInt** and returned both as strings with divisibility applied and as raw integers. The numbers in the summary also embed those strings (the LLM is never made to calculate, and nothing is rounded).
- Date → height: a binary search over the timestamps of `/blocks/{h}` (lower bound 1, upper bound the height from `/chain/info`). The from and to searches run in parallel, each of them sequentially, so there are 2 concurrent requests.
- Fetching: read `GET /statements/transaction?receiptType=8515&targetAddress=<base32>&fromHeight&toHeight&pageSize=100&order=asc&pageNumber=n` until a page with fewer than 100 entries comes back (the query names and the DTO were verified in symbol-openapi `spec/plugins/receipt/`). Beyond the limit of 200 pages (20,000 statements): `truncated: true`, `truncationReasons: ['pageLimit']`, and the summary says "narrow the period or split it with fromHeight/toHeight". `/statements/transaction` and `/blocks/*` are not cached.
- Chunked reading and adaptive shrinking (added in 0.4.0; on a live node, page 1 for 1 year (≈ 1,050,000 blocks) did not come back within 10 seconds and timed out, while half a year at a time returned 17 to 19 pages each. The REST MongoDB is slow for "a wide height range × targetAddress", and page 2 onward is fast. The timeout is not extended): split the height range with `splitHeightRange(from, to, chunkBlocks)` (ascending, no overlaps, no gaps) into pieces of about `CHUNK_DAYS` (90) days, and read them **in ascending order, one after another** (1 concurrent request). `chunkBlocks = blocksForDays(90, blockGenerationTargetTimeMs)` = `round(90 × 86,400,000 / blockTime)` (259,200 on mainnet). 90 and 7 are policy constants (`CHUNK_DAYS` / `MIN_CHUNK_DAYS`); block counts are never hard-coded. `pageNumber` starts from 1 in each chunk, and the limit of 200 pages is **the total over all chunks** (attempts that timed out are not counted). When **page 1** of a chunk gives `RestError(kind: 'timeout')`, the range from that height to the end is re-split with `shrinkChunkBlocks(len, minChunkBlocks)` = `max(ceil(len / 2), min)` and retried from its start (the shrunk length carries over to the rest of the same call, so there are at most 4 wasted timeouts in 1 call: 259,200 → 129,600 → 64,800 → 32,400 → 20,160). When a range of `minChunkBlocks` (about 7 days) or shorter times out: `isError` (host, the height range that failed, its block count, the current timeout, and "narrow it with fromHeight/toHeight or raise `SYMBOL_REQUEST_TIMEOUT_MS`"). A timeout on page 2 or later, and a RestError other than a timeout, fail as before (not hidden, not retried). No partial total is returned. The output always has `fetch { chunks (chunks read to the end), chunkBlocks (the derived initial value), splitRetries, pagesFetched }` (the top-level `pagesFetched` / `statementsFetched` stay for compatibility), 1 line about the chunking in `notes`, and, when `splitRetries > 0`, `(the node timed out on N wide queries; retried with smaller chunks)` at the end of the summary. The aggregated results (totals / daily / monthly / receipts / csv, in ascending height) are the same with chunking. The pure functions are in `src/domain/harvesting.ts`, and the fetching is `fetchHarvestStatements` of the same tool. `recent_harvest` of `symbol_delegation_diagnose` is out of scope (at most 30 days, with its own loop).
- Classification (harvester / beneficiary / unknown): in the 8515 receipts of 1 block, the 3 shares of the harvester, the beneficiary and the network are always separate receipts (2 separate ones even when the harvester and the beneficiary are the same account; verified with real mainnet data), and they are not returned in order of amount. Sort the 8515 receipts in the same statement by amount, descending; when the amounts match, within ±1 percentage point of the total, the ratio (100-B-N):B:N (3 receipts) or (100-N):N (2 receipts, a block without a beneficiary) derived from `harvestBeneficiaryPercentage`(B) and `harvestNetworkPercentage`(N), the largest = harvester and the 2nd (with 3 receipts) = beneficiary. When they do not match, what the account received in that statement is `unknown` (included in the totals, with its count in `unknownStatements` and in the summary). Never hard-code the ratios.
- Output: `summary`, `period` (kind, dates, the time zone used), `range` (fromHeight/toHeight and the times of the blocks at both ends), `totals` and `daily[]` (buckets by date boundaries in `SYMBOL_TIMEZONE`) or `receipts[]`, with the harvester / beneficiary / unknown split (`xym*` and `raw*`) and the block counts in each row, `truncated`, `notes` ("harvesting is probabilistic and varies a lot from day to day", "no currency conversion is included", and the definitions of shares and blocks).
- **Block counts** (added in 0.9.0): each row of totals, daily[] and monthly[] has `blocks` (blocks in which this account received a receipt), `blocksHarvested` (blocks it harvested itself = it received the harvester share; always equal to `receiptsHarvester`) and `blocksBeneficiaryOnly` (blocks another account harvested that paid it only the beneficiary share; mostly delegators of this account's node). Blocks of statements that could not be classified count only in `blocks`. Receipts are shares, not blocks. An operator that is also its own node's beneficiary receives 2 receipts (harvester and beneficiary) for 1 block of its own, so `receiptsBeneficiary` is not the number of delegators' blocks (a real case in which Claude Desktop misread "357 beneficiary receipts = delegators' blocks"; in fact 317 of the 357 were shares of its own blocks, and the delegators' blocks were 40). So line 2 of the summary gives "Blocks: N harvested by this account, M harvested by others that paid it only the beneficiary share …" and the number of beneficiary receipts that come from its own blocks. The definition of beneficiary in the description and the notes was also changed, to "the share paid to the beneficiary that the harvesting node names; an account that is its own node's beneficiary also receives it from its own blocks" (the earlier "blocks of others" was wrong). The aggregation counts 1 block per height (`addBlock` in `src/domain/harvesting.ts`), and the receipts of 1 block fall on the same date, so "the count for a month = the sum of the daily counts in that month" also holds. `addBlock` counts each block as exactly 1 of harvested / beneficiary only / unrecognised, and counts on the spot the beneficiary receipts in its own blocks (`beneficiaryReceiptsInOwnBlocks`) and the blocks that could not be classified (`blocksUnrecognised`) (both are for the summary, not output fields; the tool never estimates them by subtraction). Blocks are handled with a non-empty array type (`[HarvestRow, ...HarvestRow[]]`).
- Reference: `GET /statements/transaction` (TransactionStatementPage → the BalanceChangeReceiptDTO `{ type, mosaicId, amount, targetAddress }` in `statement.receipts[]`; `meta.timestamp` is the block's network timestamp), `GET /blocks/{height}`, `GET /chain/info`, `GET /accounts/{id}`. The table of receipt type names is imported from catbuffer `receipt_type.cats` (`src/domain/receipttype.ts`).
- `granularity: monthly` (added in 0.2.0): buckets by calendar month in `SYMBOL_TIMEZONE` (UTC when it is unset) and returns `monthly[]` (`{ month: 'YYYY-MM', ...the same columns as daily }`, in ascending month key). `src/domain/harvesting.ts` aggregates it through the same BigInt path and with the same date key (its first 7 characters) as the daily buckets, so "a month's total = the sum of the daily totals in that month" holds by construction (checked against fixed values in unit tests). The summary **keeps the 1 line with the period total first**, and after the line with the block split adds 1 line per month (`2026-08: 674 receipts, 23,237.845492 symbol.xym; 357 blocks: 317 harvested by this account, 40 by others (receipts 317 harvester / 357 beneficiary)`; when some blocks could not be classified, it says `40 by others, 1 not recognised`, so that the block split adds up to the total; thousands separators only in the summary). The number of lines is the number of months, so it is not truncated. The output forms of daily / receipt do not change.
- `output: csv` (added in 0.2.0): **an explicit exception to §2-4 "the text is the JSON string of structuredContent"**. `structuredContent` stays JSON (it meets the outputSchema) and has `csv: string` (null for json), and `content[0].text` is the CSV body itself (the `renderText` hook in `_shared.ts`; other tools stay JSON). The rows follow granularity (daily → 1 row for 1 day, monthly → 1 row for 1 month, receipt → 1 row for 1 receipt, with the limit 50 / 500 of `format` applied; a truncation is stated in the summary). Columns: daily / monthly are `period,receipts,xym,raw,receipts_harvester,xym_harvester,raw_harvester,receipts_beneficiary,xym_beneficiary,raw_beneficiary,receipts_unknown,xym_unknown,raw_unknown,blocks,blocks_harvested,blocks_beneficiary_only` (the last 3 columns were appended at the end in 0.9.0, so the positions of the earlier columns do not change), and receipt is `height,timestamp_utc,timestamp_local,kind,xym,raw` (`timestamp_local` is empty when `SYMBOL_TIMEZONE` is unset). A header row, LF line endings (also after the last row), UTF-8, no BOM, no total row, no thousands separators. The values are only numbers and ISO dates and times, but they must always go through RFC 4180 quoting (`src/domain/csv.ts`).

**`symbol_finality_participation`** (added in 0.2.0; registered at the end of the tool array without changing the existing order) — `account` (an address, public key or namespace name; the resolution rules in §5 "Common conventions"), `epoch` (optional; when not given, `latestFinalizedBlock.finalizationEpoch` of `/chain/info`), `epochs` (1 to 20, default 1; N consecutive epochs going back from `epoch`; fetched in parallel, and the concurrent requests stay within RestClient's limit of 4), `format` (concise omits `stages` for epochs that are `participated`; detailed includes them for every epoch).
The question it answers: "Did this account's voting key actually take part in the finalization votes of the given epoch?". Used to verify a key renewal (whether it is actually voting with the new key) and for the monthly health check of a voting node. `symbol_voting_key_status` answers "when does it expire", and this tool "is it actually used".
- Verified facts (2026-09-13; a human checked a real proof of mainnet epoch 4010): the response of `GET /finalization/proof/epoch/{epoch}` is `{ version, finalizationEpoch, finalizationPoint, height, hash, messageGroups: [{ stage, height, hashes[], signatures: [{ root: {parentPublicKey, signature}, bottom: {parentPublicKey, signature} }] }] }`. messageGroups has 2 entries (stage 1 = precommit, stage 0 = prevote), with 17 signatures each. **The voting public key registered on the account matches `signatures[].root.parentPublicKey` exactly and does not appear in `bottom.parentPublicKey` (an intermediate key)**. So participation is judged by "the set of root keys contains a registered key". The meaning of stage was verified in `StageEnum` of OpenAPI v1.0.4 (0 = Prevote, 1 = Precommit, 2 = Count). There were 17 signatures while nodewatch listed 18 voting nodes, so detecting this difference (the nodes that did not take part) is 1 of the aims.
- Verified facts (2026-09-21; a human checked a real proof of mainnet epoch 4027; fixed in 0.5.0): **messageGroups is not always "1 entry per stage". The same stage at the same height can be split into several groups** (the lists of hashes voted for differ; epoch 4027 has 3: stage 1 ×1, and stage 0 as 2 groups at the same height 5796428 with 2 and 15 signatures, 17 in total). The key of 1 voter appears in only 1 of those groups, so **the judgment is made per stage, not per group**: group messageGroups by stage, and a stage is signed when a registered key is in the union of the root keys of all the groups of that stage. The rule up to 0.4.0, "the account's key is in every group", misjudged an account that had voted correctly as missed on such a proof, and the summary contradicted itself as well ("signed prevote and precommit only, not prevote").
- Processing: fetch the voting key list of `/accounts/{id}` and `/chain/info` in parallel → for each target epoch, fetch the proof with `getOrNull` (a 404 becomes `status: 'unavailable'`, not `isError`; only when every epoch is 404, `isError` + a hint; when the requested epoch is later than the latest finalized epoch, the hint says "proofs exist only for finalized epochs"; when the proof's `finalizationEpoch` differs from the one requested, `invalid_response`) → group messageGroups by stage, build the union of the root keys of all the groups for each stage, and match it against the registered keys → separately judge whether there is a key that should be valid in that epoch (startEpoch ≤ e ≤ endEpoch). The judgment is a pure function in `src/domain/finality.ts`.
- Judgment: a match in **every stage present in the proof** (in any group of the stage) → `participated` (the proof's signatures take precedence over the current key list; a signature by a key already unlinked is also participated). A stage without a match, with a valid key → `missed`. The signed stages are listed by `describeSignedStages` (`src/domain/finality.ts`; shared by the tool's summary and the detail of CLI check): all → `signed prevote and precommit`, some → `signed prevote, not precommit`, none → `signed no stage (not prevote, not precommit)`. Each stage name appears only once, so the sentence never contradicts itself. The epoch line of the summary is `Epoch N: participated, signed prevote and precommit (prevote 17 signatures in 2 groups, precommit 17 signatures; …)` (`in N groups` is left out when there is only 1 group). No valid key → `no_active_key`. No proof → `unavailable`.
- Output: `summary`, `account: { address, publicKey, votingKeys[{ publicKey, startEpoch, endEpoch, activeForEpoch }] }`, `current`, `requested`, `epochs[{ epoch, status, finalizationPoint, height, proofHash, stages[{ stage, stageName, height, heights[], groups, signatureCount, participated, matchedPublicKey }], participatedAllStages }]` (newest epoch first; `stages[]` has **1 element per stage**: `groups` = the number of message groups of the stage, `heights` = the heights of the groups (distinct, ascending), `height` = their minimum (the same value as before when there is 1 group), `signatureCount` = the total number of signatures over all the groups of the stage), `totals { checked, participated, missed, noActiveKey, unavailable }`, `warning` (a warning about whether the account can vote "now", judged against the current finalizationEpoch. No key covers the current finalizationEpoch → a warning that it cannot take part (judged regardless of the requested epochs) / the first requested epoch equals the current finalizationEpoch and is missed → a warning that it is not voting / otherwise null. `no_active_key` / `missed` of past epochs stay in `epochs[].status`; having no key in a historical epoch is normal), `notes` (`signatureCount` is the number of voters that signed, and this server cannot know the total number of registered nodes / `unavailable` says nothing about whether the account voted). **Other nodes' public keys are never output**.
- Fixture: `test/fixtures/mainnet/finalization-proof-epoch.json`, a real proof with every `parentPublicKey`, `signature`, `hashes` and `hash` replaced by synthetic values derived from `H("fixture:…")` (rules in `test/fixtures/README.md`). The root key of the account under test is the existing synthetic voting key `H("fixture:voting-key-2")` (epochs 3700 to 4059, including 4010). epoch / point / height / stage / the signature count (17) / the number of hashes (21) keep their real values. The values of the raw file are never written into the repository.
- Reference: `GET /finalization/proof/epoch/{epoch}` → `FinalizationProofDTO` (`MessageGroup` → `BmTreeSignature` → `ParentPublicKeySignaturePair`, verified in OpenAPI v1.0.4), `GET /accounts/{id}`, `GET /chain/info`.

**`symbol_delegation_diagnose`** (added in 0.2.0; registered at the end of the tool array without changing the existing order) — `account` (an address, public key or namespace name; pass the main account), `recentDays` (1 to 30, default 7; how many days back to look for harvested blocks), `format` (concise sets `hint` to null for the checks that are ok; detailed gives every check a `hint`).
The question it answers: "Is this account's delegated harvesting active? If not, where does it stop?". A delegator diagnoses their own account, and a node operator a delegator's account (the equivalent of the delegation check in Harvest Checker / XEMBook). `symbol_harvesting_status` only answers "is it in the node's unlocked list", and `symbol_harvesting_income` only totals the rewards.
- **The principle of what can be verified**: only `SYMBOL_NODE_URL` can be contacted, so the node-side state (unlocking, the delegation request) can be verified **only when the account delegates to the configured node**. When the account's node key differs from `nodePublicKey` of `/node/info`, the node-side checks are `unknown`, saying "cannot be verified because the node delegated to is not the configured node". Other nodes are never asked.
- Every threshold comes from `/network/properties`: `minHarvesterBalance` / `maxHarvesterBalance` (**compared with the balance of `chain.harvestingMosaicId`**; it exists in the OpenAPI `ChainPropertiesDTO` as "Mosaic id used to provide harvesting ability". On mainnet / testnet it has the same value as `currencyMosaicId`, but the harvesting requirement is defined with harvestingMosaicId. The parser treats it as required (`parseHexId`), and reading `/network/properties` fails when it is not 16-character hex, so there is no fallback), `importanceGrouping`, `harvestBeneficiaryPercentage` / `harvestNetworkPercentage` (for classifying receipts).
- Checks (`checks[]` in a fixed order, each `{ id, status: ok|warn|fail|unknown, detail, hint }`):
  1. `account_exists` — fail when `/accounts/{id}` is 404. All the later checks are then unknown, `recentHarvest: null`, and it is not `isError`.
  2. `balance_in_range` — fail below the minimum, fail above the maximum (above maxHarvesterBalance the account cannot harvest).
  3. `importance_positive` — ok when `importance > 0`. 0 with the balance ok → warn (the next recalculation height `(floor(h / G) + 1) × G` and the remaining blocks go in the hint; `src/domain/delegation.ts`). 0 with the balance failing → fail.
  4. `linked_key` / 5. `vrf_key` / 6. `node_key` — whether each exists in `supplementalPublicKeys`. fail when missing (pointing to AccountKeyLink / VrfKeyLink / NodeKeyLink).
  7. `node_key_matches_configured_node` — ok when equal to `nodePublicKey` of `/node/info` (optional in the OpenAPI `NodeInfoDTO`), warn when different, unknown when there is no node key or no `nodePublicKey`.
  8. `unlocked_on_node` — judged only when 7 is ok. ok when the linked key is in `/node/unlockedaccount` (`unlockedAccount`, singular), fail when it is not (not accepted, not resent after a restart, or the unlock slots are full; ask the operator). unknown when 7 is warn/unknown, or when `/node/unlockedaccount` fails (even on a 5xx, the other checks are still returned).
  9. `account_type` — ok when `accountType` is 1 (OpenAPI `AccountTypeEnum`: balance-holding account linked to a remote harvester = Main). 2 / 3 (the Remote kinds) are warn "pass the main account", and 0 is warn too.
  10. `recent_harvest` — the HarvestFee (8515) receipts of the last `recentDays` days. The heights of the period are estimated from the measured average block time (`getAverageBlockTime`) (stated in `notes`; the binary search is not used because of the number of requests it takes). `/statements/transaction?...&order=desc` in pages of 100, up to 20 pages. The collected statements go through `aggregateHarvestIncome`, the same as in `symbol_harvesting_income`, and **only the receipts of the harvester share are counted** (1 receipt for 1 block harvested; a block of its own in which it is also its own node's beneficiary counts as 1 as well. The beneficiary share is excluded because it does not show that the account harvested: it comes from a block another account harvested, or, when the account is its own node's beneficiary, it is the second receipt of a block that its harvester share already counts). Blocks that could not be classified (`blocksUnrecognised`) are not counted and are mentioned separately in the detail text (fixed in 0.9.1; before that, unknown was counted too, so a block of its own that could not be classified counted as 2, and a delegator's block counted as "harvested"). Judgment: 1 or more → ok (when some blocks could not be classified, "Not counted: …" at the end of the detail). 0, with 1 or more blocks that could not be classified → unknown (hint: the shares do not match harvestBeneficiaryPercentage / harvestNetworkPercentage, so it cannot tell whether the account harvested or only got the beneficiary share; with no other fail, the verdict is cannot_verify). 0, with none of those and no fail → warn ("active, but no hit in the last N days; with a small importance, the gaps are long"); with a fail → unknown. When it stops at 20 pages, the notes say "read the newest 2,000 statements (blocks in which it received a reward, as harvester or as beneficiary), so the count is a lower bound". `recentHarvest { days, receipts, lastHeight, lastTime }` (`receipts` is the number of harvester receipts = the number of blocks harvested; the shape of the field does not change).
  11. `delegation_request_found` — whether a delegation request transfer exists. Implemented after checking the sources (never written from guesses): catapult `plugins/txes/transfer/src/plugins/TransferPlugin.cpp` registers `CreateTransferMessageObserver(0xE201735761802AFE, recipient, …)`, with `recipient = PublicKeyToAddress(encryptionPublicKey)` (node.key.pem = the REST `nodePublicKey`). `observers/TransferMessageObserver.cpp` compares the first 8 bytes as an LE uint64 and requires `MessageSize > 8`. The same as `DELEGATION_MARKER = 'FE2A8061577301E2'` in the SDK's `sdk/javascript/src/symbol/MessageEncoder.js`. The constant is `PERSISTENT_DELEGATION_MARKER` in `src/domain/message.ts` (with a comment citing the source). Processing: from `GET /transactions/confirmed?signerPublicKey=<pk>&recipientAddress=<publicKeyToAddress(nodePublicKey)>&type=16724&pageSize=100&order=desc&pageNumber=1` (`embedded` is false by default, so inner Txs are out of scope), the newest 1 whose `message` starts with the marker. ok when found (height, time), warn when not (information only; it does not affect the verdict). unknown when 7 is warn/unknown, the public key is zero, or there is no `nodePublicKey`.
- verdict: any fail → `not_active`. No fail but some unknown → `cannot_verify`. Otherwise → `active` (active even when `recent_harvest` / `delegation_request_found` are warn).
- Output: `summary` (line 1 `delegated harvesting: active | not active | cannot verify (<address>).`, then the gist of each fail / warn, and for cannot_verify the items that could not be verified), `network`, `address`, `verdict`, `checks[]`, `account { balanceXym, rawBalance, importance, importanceHeight, accountType { code, name }, keys { linked, vrf, node } }` (keys are hex or null), `node { configuredNodePublicKey, unlockedCount }` (null when they cannot be fetched), `recentHarvest | null`, `notes[]` (unlockedaccount is self-reported and not backed by the chain / delegation to another node cannot be verified / importance is updated every importanceGrouping / the heights of the period are estimates).
- Reference: `GET /accounts/{id}`, `GET /chain/info`, `GET /node/info` (`nodePublicKey`), `GET /node/unlockedaccount`, `GET /statements/transaction`, `GET /transactions/confirmed` (`signerPublicKey` / `recipientAddress` / `type` / `order` / `pageSize` / `pageNumber` verified in the OpenAPI), `GET /blocks/{h}` (average block time).

**`symbol_node_health`** (added in 0.3.0; registered at the end of the tool array without changing the existing order) — `format` only. No account argument.
The question it answers: "Is the configured node running healthily right now (DB / API node / storage / time / finalization lag)?". It complements `symbol_node_status` (version, sync, peer count) instead of replacing it. The first tool to look at before and after an OS migration.
- Fetching (in parallel; serialised by RestClient's semaphore of 4): `GET /node/health`, `GET /node/storage`, `GET /node/time`, `GET /chain/info`, `GET /node/info`, `ctx.getNetworkData()`. The schemas are `NodeStorageSchema` / `NodeTimeSchema` in `src/client/schemas.ts`.

When `/node/health` itself fails (timeout / unreachable / an http error other than 503 / invalid), `api_node` and `db` are fail.
- Checks (in a fixed order, each `{ id, status: ok|warn|fail|unknown, detail, hint }`; the common `CheckSchema` / `check()` / `stripOkHints()` in `src/tools/_checks.ts`):
  1. `api_node` — ok when `status.apiNode === 'up'`, otherwise fail
  2. `db` — ok when `status.db === 'up'`, otherwise fail
  3. `storage_consistent` — ok when `|numBlocks − height|` is within `max(1, ceil(60000 / blockGenerationTargetTime))` blocks ("1 minute's worth"; mainnet 30 s → 2), warn when beyond it. unknown when `/node/storage` or `/chain/info` cannot be fetched

**`symbol_version_drift`** (added in 0.3.0; registered at the end of the tool array without changing the existing order) — `format` only.
The question it answers: "Has the configured node's version fallen behind the network majority?". A node that falls behind the majority has its connections refused by other nodes, so this is the most important thing to check after an OS migration.
This tool's output has no `hint` field. The "advice" in this section and in §7 is the 1 line starting with `- ` that goes on line 2 of the summary when the verdict is not ok (apart from the distribution lines that follow it in detailed; the CLI check of §13 uses this line as the hint).
- Fetching: `GET /node/info` (the configured node; `decodeVersion`; a failure is fatal), `GET /node/server` (`ServerInfoDTO { serverInfo: { restVersion, sdkVersion, deployment } }`; v1.0.4 makes `sdkVersion` required but has no property definition for it, and older catapult-rest has no `deployment`, so everything except `restVersion` is optional + loose; a failure gives `restVersion: null`), `GET /node/peers` (`NodeInfoDTO[]`; received as an array with `NodePeersRawSchema`, and each element checked with `NodePeerSchema.safeParse`. Broken elements, another `networkGenerationHashSeed`, and the configured node's own `publicKey` are counted in `ignored` and left out. A failure gives 0 peers + a note), and, when `SYMBOL_REFERENCE_NODES` is set, `/node/info` of each of `ctx.referenceClients()` (the same try/catch as `probe` of `symbol_network_compare`; unreachable nodes and other networks are left out with a note).
- Version 0 (0.0.0.0) means "the version is unknown", not a real version (added in 0.9.0). catapult creates the peers it reads from its peers files (`knownPeers`) with `NodeMetadata(networkFingerprint, name)`, and their version stays `NodeVersion()`, that is 0 (`client/catapult/src/catapult/config/PeersConfiguration.cpp`, `ionet/Node.h`). `/node/peers` returns 0 until the node learns the real version. Such peers and reference nodes (`isUnreportedVersion`) are left out of the distribution, the majority and `newerShare`, and are counted in `sample.unknownVersion` (when it is 1 or more, this is said at the end of line 1 of the summary and in the notes). They used to be counted as 1 version, which inflated the sample and lowered `newerShare`, and when 0 was common it became the majority, so the configured node could be judged "newer than the majority" = ok. When every peer's version is 0, the sample is empty, so `unknown`, with the advice "the peers have not reported their versions yet". The notes are split by origin: for peers, the explanation of the peers files; for reference nodes, "returned 0 from its own `/node/info`". When the sample is empty and `SYMBOL_REFERENCE_NODES` is set, the advice does not recommend setting it and says "no reference node returned a usable version (see the notes)". When the configured node's `/node/info` returns 0, it is treated as unknown in the same way (own is passed as null to `versionDistribution` and `deriveVersionDriftVerdict`): the verdict is `unknown`, `newerShare` is null, the distribution and `majorityVersion` are returned as they are, and the advice is "check the version on the node and compare it with majorityVersion". Comparing with 0 would make every node in the sample a newer version and give a false far_behind ("update now").
- Aggregation (`src/domain/version.ts`): `compareVersions` compares component by component as numbers (a missing component is 0; `1.0.3.10 > 1.0.3.9`, `2.10.0 > 2.4.4`; never a string comparison). `versionDistribution` sorts by count descending → version descending (**on a tie, the newer version is the majority**: in a transition the network converges on the newer one, so this errs toward warn). `newerShare` = the share of versions newer than the configured node's.
- verdict (`deriveVersionDriftVerdict`): the configured node's version is unknown (own is null) → `unknown` / size 0 → `unknown` (advice: a problem with the peer connections themselves; look at `symbol_node_health` / `symbol_node_status`, or `SYMBOL_REFERENCE_NODES`; when that is set, look at the notes) / `newerShare ≥ 0.75` (`FAR_BEHIND_SHARE`) → `far_behind` ("connections may start being refused") / `own < majority` **or** `newerShare ≥ 0.5` (`BEHIND_SHARE`; even when the configured node runs the most common version, it is falling behind once the newer versions together hold a majority) → `behind` / otherwise `ok` (also ok when newer than the majority). The thresholds are policy constants, not network constants.
- Output (summary first): `summary` / `network` / `verdict` / `node { version, versionRaw, restVersion: nullable }` / `sample { size, source: 'peers' | 'peers+reference', peers, referenceNodes, ignored, unknownVersion }` (`size`, `peers` and `referenceNodes` count the ones whose version is known and that entered the distribution) / `distribution [{ version, count, share }]` / `majorityVersion: nullable` / `newerShare: nullable` / `farBehindShare` / `notes[]` (the sample is part of the peers the configured node knows, and the full picture is on nodewatch / the peers' host, friendlyName and publicKey are untrusted and **never output** (only versions and counts) / the exclusion rules).
- Reference: `GET /node/info`, `GET /node/server`, `GET /node/peers`, and `GET /node/info` of the reference nodes.

**`symbol_harvester_watch`** (added in 0.3.0; registered at the end of the tool array without changing the existing order) — `mode` (`compare` = read only / `compare_and_save` = the default, compare and append the current list / `save_only` = append without comparing), `format` (detailed outputs `current.keys` and `history.entries`).

**`symbol_holdings_value`** (added in 0.7.0; registered at the end of the tool array without changing the existing order) — `account` (required; an address, public key or namespace name), `unitPrice` (required; a **string**: a positive number in base-10 notation, at most 12 fractional digits, at most 40 characters in all (`MAX_PRICE_LENGTH`; the length before normalisation). 41 characters or more, exponent notation, commas, currency symbols, signs, `12.`, `.5`, empty and 0 are checked inside `run` and give `isError` + a hint. Leaving this to zod's `.min(1)` or a regex gives the SDK's generic message with no hint, so the schema stays `z.string()`), `currency` (required; `^[A-Z]{3,6}$`; also checked inside `run`), `priceSource` (optional; at most 80 characters; echoed through `text.clean` as untrusted (the removal and counting path of §2-8; the removed characters count in `invisibleCharactersRemoved`); when nothing is left, it counts as not given (null)), `priceAsOf` (optional; at most 40 characters; the only check is that `Date.parse` accepts it after removal with `text.clean`, and the value after removal is echoed without reformatting (when nothing is left, it counts as not given); no strict ISO 8601 regular expression), `mosaic` (optional; a hex id or an alias name; by default the currency mosaic; reuses `resolveMosaicInput`, and the currency mosaic needs no extra request), `decimals` (optional; an integer from 0 to 12; the decimals `amount` is rounded to; the schema stays `z.number()`, and the value is checked inside `run`, giving `isError` + a hint), `format` (the JSON is the same; detailed adds 1 line with the value before rounding to the summary, only when it was rounded).
The question it answers: "What are this account's XYM holdings worth in total at a unit price of X yen?". **The unit price is supplied by the caller.**
- **The principle of not handling prices, and why this design keeps to it.** The rule of §2-7, "outbound traffic goes only to `SYMBOL_NODE_URL` and `SYMBOL_REFERENCE_NODES`", would be broken by calling a price API. Prices change, their values depend on where they come from, exchange APIs come with terms of use and keys, and which one to believe is the user's decision; the server cannot hold "the right price". So this tool takes the price as **input** and only multiplies. The server does not check whether the origin (`priceSource`) and the time (`priceAsOf`) of the unit price are true: it echoes them after the removal of §2-8 (and checks only that `priceAsOf` is a date, as in the arguments above), and the summary says "price supplied by the caller: …", so whoever reads the answer can always see "when and where the unit price came from". Getting the unit price is the caller's job (a web search, another MCP server that returns prices, the user's input); the description and the instructions say so explicitly, and the model is told "never compute balance × unit price yourself" (to avoid floating-point rounding and mixed-up digits; the server computes the product deterministically with BigInt). The test "no fetch to anything but `SYMBOL_NODE_URL`, even with reference nodes set" in `test/tools/holdings_value.test.ts` fixes that no price API is called.
- Processing (all in integer arithmetic; the pure functions are in `src/domain/price.ts`): `parseDecimalString` splits `unitPrice` into the integer `scaled` and the number of fractional digits `decimals`, and normalises it by dropping the leading zeros of the integer part and the trailing zeros of the fraction (`"012.340"` → `1234n` / 2 / `"12.34"`; so that the number of digits of `exact` does not depend on how the input was written) → `ctx.getNetworkData()` → resolve the mosaic → `fetchAccount` → `mosaicBalanceOf` (reusing `domain/rank.ts`) → `multiplyAndRound`: `raw = balanceRaw × scaled`, `exact` is a string with `divisibility + decimals` fractional digits (`formatScaled`; `formatAmount` is not used, because it caps divisibility at 18), and `amount` is `roundScaled` = `(x + unit/2) / unit`, rounded half up. `roundingRule` decides the digits to round to, in this order: (1) the `decimals` argument when given (`caller`), (2) for a currency Intl knows, `new Intl.NumberFormat('en', { style: 'currency', currency }).resolvedOptions().maximumFractionDigits` (`currency`; "knows" means that `new Intl.DisplayNames(['en'], { type: 'currency', fallback: 'none' }).of(code)` returns a name. `Intl.supportedValuesOf('currency')` is not used, because it lists only the currencies ICU considers "common and not obsolete" and leaves out CLF, UYW and XAU), (3) anything else (BTC, USDT and so on) is not rounded (`none`). No ISO 4217 table is built in. `Intl.DisplayNames` and `NumberFormat` are created at call time (on a Node without Intl, only this lookup fails and becomes `none`, and the server as a whole does not go down), and only the digits of the currencies Intl knows are cached per process (unknown codes are not kept, so the cache never grows beyond CLDR's list of currencies, whatever codes callers pass; failures in an environment without Intl are not kept either). Special codes that CLDR has names for (XXX, XTS, XAG and so on) are also rounded to CLDR's digits (mostly the default 2). The values depend on the ICU / CLDR of the running Node.js, and CLDR differs from ISO 4217 for some codes (ICU 78.3 / CLDR 48: HUF 0, IDR 0, IQD 0, IRR 0). **Safety rule**: a product other than 0 that would round to 0 is not rounded (`rounds_to_zero`; this keeps a small XAU amount at CLDR's default 2 digits from becoming 0.00; the same applies when `decimals` is given). When not rounded, `amount` is `exact` without its trailing zeros (`trimFraction`; the value does not change). No derived values (such as the value per 1,000 XYM) are output.

## 6. Domain knowledge and pitfalls

**Addresses**: 24 bytes. Base32-encoded with the trailing `=` removed: **39 characters**. The first character is `N`=mainnet, `T`=testnet. The API's JSON gives addresses in **hex (48 characters)**, so convert them to base32 for display. `/accounts/{id}` can be looked up by a base32 address or by a public key. An address is derived from a public key by SHA3-256 → RIPEMD-160 → adding the network byte → checksum (the first 3 bytes of SHA3-256). For the implementation, refer to `SymbolFacade.network.publicKeyToAddress` of `symbol-sdk` (npm), or verify with its test vectors.

**Amounts**: all integer strings. XYM has divisibility 6 (`1000000` = 1 XYM). The XYM mosaicId on mainnet is `6BED913FA20223F8` (alias `symbol.xym`). Get the divisibility of other mosaics from `/mosaics/{id}`.

**Parsing `/network/properties`**: every value is a string; numbers have **apostrophe separators** (`"3'000'000'000'000"`) and times have **units** (`"30s"`, `"15m"`). Write a dedicated parser and unit-test it.

**Timestamps**: `block.timestamp` is in **milliseconds** from `epochAdjustment`. Wall-clock time (ms) = `epochAdjustment(seconds)×1000 + timestamp`. The epochAdjustment of mainnet is 1615853185 (= 2021-03-16 00:06:25 UTC). **Read the value from `network.epochAdjustment` of `/network/properties`** (in the form `"1615853185s"`).

**Epoch ⇄ height** (`G = chain.votingSetGrouping`, 1440 on mainnet):
```
heights of epoch e = (e-2)×G + 1  to  (e-1)×G
epoch of height h  = floor((h-1)/G) + 2
```
Verified with 2 data points of real mainnet data: finalized height 5,755,504 → epoch 3998, 5,763,316 → 4004. **Confirm with an integration test that this formula agrees with `latestFinalizedBlock` of `/chain/info`.** The expiry height of a voting key with `endEpoch = E` is `(E-1)×G`.

**Estimating the date of a future height**: use the **measured average**, not `blockGenerationTargetTime` (30s). It is computed as the timestamp difference between the first and the last of the latest N blocks (default 10,000) ÷ N (measured 30.03 s on mainnet, 2026-09). State "estimated" and the measured value in the output.

**Node roles**: `roles` is a bit flag. 1=Peer, 2=API, 4=Voting. 7 = all.

**Version**: `version` is 4 bytes packed into an integer, major.minor.patch.build from the top. `16777993 = 0x01000309 → 1.0.3.9`.

**Transaction types**: `type` is a number (e.g. 16724 = Transfer). **Import the table of names mechanically from the `TransactionType` enum of `symbol-sdk` or from the official documentation. Never write it from memory.** Main types: Transfer, AggregateComplete, AggregateBonded, AccountKeyLink, VotingKeyLink, VrfKeyLink, NodeKeyLink, MosaicDefinition, MosaicSupplyChange, NamespaceRegistration, AddressAlias, MosaicAlias, HashLock, SecretLock, SecretProof, the various Metadata/Restriction types, MosaicSupplyRevocation.

**Messages**: the `message` of a transfer transaction is hex. The first byte is the type (`00`=plain, `01`=encrypted), and the rest is the body (UTF-8 when plain). An encrypted message cannot be decrypted, so it is reported as "encrypted message (cannot be decrypted)". **The body is a string third parties can write** (§2-8).

**Namespace name → ID**: fold the name of each level with SHA3-256 (`generateNamespaceId`). Verify with the implementation or the test vectors of `symbol-sdk`. `symbol.xym` → namespace ID `E74B99BA41F4AFEE`, whose alias target is mosaic ID `6BED913FA20223F8`.

**Voting keys**: `{publicKey, startEpoch, endEpoch}` in `supplementalPublicKeys.voting.publicKeys[]`. **Expired keys stay registered and keep using up the slots of `maxVotingKeysPerAccount` (3 on mainnet).**

**Paging**: search endpoints return `{ data: [], pagination: { pageNumber, pageSize } }`.

**Ports**: 3000 (http) and 3001 (https). Some nodes open only one of them. Use the URL the user gives as it is, and never change the port on your own.

**Caching**: `/network/properties` is fetched only once per network within the process. `/chain/info`, `/node/*` and `/accounts/*` are not cached.

**HTTP hygiene**: `AbortSignal.timeout(SYMBOL_REQUEST_TIMEOUT_MS)` and `User-Agent: <package-name>/<version>` on every request, a response size cap (e.g. 5MB), and a concurrency limit (e.g. 4). Validate the JSON a node returns against a schema before using it (when the shape differs, return `isError` saying "the node's response is not what was expected").
- **Redirects are never followed**. Requests are sent with `redirect: 'manual'`, and a redirect (the Fetch Standard's redirect statuses 301, 302, 303, 307 and 308, and the opaqueredirect a fetch that follows the specification returns) has its body discarded and becomes `RestError('redirect')`. Other 3xx (300, 304 and so on) stay HTTP errors as before (the body is discarded). Location is a string the node decides, so it is neither followed nor put in the wording. The wording of the advice is in 1 place, `REDIRECT_ADVICE` (`src/config.ts`), and the tool's isError, a failed start of CLI check (exit 3) and a failed start of the server (the `failed to start:` line) all give the same sentence. A redirect from a reference node is shown by `symbol_network_compare` as `redirect: …` and by `symbol_version_drift` as a note that it "returned a redirect".
- **The size cap is applied on the stream**. When Content-Length is over the cap, the body is refused unread, and while reading, the running total of bytes is counted and the reader is cancelled as soon as it goes over (a compressed response is counted in bytes after decompression). A body that is not read (an HTTP error, a redirect, a Content-Length over the cap) is discarded with `body.cancel()`, so the connection is not held.
- **A 404 for a missing route is an error** (added in 0.9.1; Fail loudly). The body of a 404 is read under the same cap and used only for the judgment (never put in the wording). When it has restify's "no such route" shape (`code` is `ResourceNotFound` and `message` starts with `/` and ends with ` does not exist`), it becomes `RestError('route_not_found')`, and `getOrNull` does not turn it into null either (the tools give isError: "the node does not provide this endpoint; a bug in this server, or a catapult-rest version that does not support it"). `no resource exists with id '…'`, an empty body and any other shape stay `not_found` as before (`getOrNull` gives null). Up to 0.9.0, `symbol_account_get` called the nonexistent `/accounts/{address}/multisig` and read this 404 as "not a multisig". The test harness also returns the same "no such route" 404 for any path without a stub, so when a path is wrong, even a test that expects null or not_found fails. A test that expects "no data" stubs that path explicitly with `resourceNotFound(id)` (never with a wildcard: a prefix match like `/accounts/*` hides exactly this mistake).
- **Paths and queries are ASCII letters, digits and `_` only** (query values may also contain `-`; `SAFE_REQUEST_PATH`). Tools validate their arguments before building a path, and build queries with `URLSearchParams`. The RestClient check is the net under that: a path that does not fit is not sent and becomes an internal error.

## 10. What not to do

- Never create an argument that accepts a private key, mnemonic or password. Never sign or announce transactions
- **Never take a URL as a tool argument**. Never hard-code a node URL in the code (except mock values in tests)
- Never generate tools mechanically as 1 REST endpoint = 1 tool
- Never hard-code network constants in the code (the generationHashSeed table is the only exception)
- Never contact anything but `SYMBOL_NODE_URL` and `SYMBOL_REFERENCE_NODES`
- Never switch implicitly on an error, as in "fall back to testnet". Return a failure as a failure
- Never use `console.log` (stdout is for JSON-RPC only). Log with `console.error`
- Never depend on the logging / sampling / roots features of MCP (deprecated in the 2026-07-28 specification)

## 13. CLI mode (`check`; added in 0.5.0, at the end, without renumbering the existing sections)

**Purpose**: judge a node's health with 1 command from cron, without an MCP client, and exit non-zero when something is wrong. **No notification is sent** (that is left to cron's `MAILTO`; no outbound traffic is added). What the binary does when started without arguments (the MCP server, stdio), `--help` / `--version`, and unknown argument → exit 2 do not change.

```
symbol-mcp-server check [--account <address|publicKey|namespace>] [--warn-days <n>] [--format text|json] [--quiet]
```

- The environment variables are shared with MCP (`createAppContext` = loadConfig → RestClient → resolveNetwork → AppContext is placed in `src/context.ts`, and both the server and check use it). `--warn-days` is an integer from 1 to 120, default 14; `--format` defaults to text; `--quiet` prints nothing on exit 0.
- Argument parsing is hand-written (`parseCliArgs` in `src/cli.ts`). Both `--flag value` and `--flag=value`. An unknown flag, a positional argument, a missing value, a duplicate, a value out of range, `--quiet=…`, or invalid `--account` syntax (`classifyAccountId`; no network access) gives exit 3. `check --help` is the overall help.

**Judging only maps the results of the existing tools**. `runCheck(ctx, options)` (`src/cli/check.ts`) calls `tool.run(ctx, input)` directly for the 5 items, **in a fixed order, one after another** (going through neither the MCP transport nor the result formatting). Do not change the tools' thresholds or logic for the CLI. The mapping tables `mapNodeHealth` / `mapVersionDrift` / `mapHarvesterWatch` / `mapVotingKeys(output, warnDays)` / `mapFinality` and `decideExit` are pure functions, and their arguments are structural types of "only the fields they read" (a tool's output can be passed as it is).

| # | id | How it is called | status |
|---|---|---|---|
| 1 | `node_health` | `symbol_node_health` | healthy → ok / degraded → warn / unhealthy → fail |
| 2 | `version_drift` | `symbol_version_drift` | ok → ok / behind → warn / far_behind → fail / unknown → warn |
| 3 | `harvester_watch` | `symbol_harvester_watch`, mode `compare_and_save` | `comparison.deltaCount < 0` → warn, `saved === false` (a write failure) → warn, otherwise ok (a baseline is ok too). When `ctx.config.stateDir` is unset, the tool is not called and the item is skip (the detail is the tool's `UNSET_NOTE`) |
| 4 | `voting_key_status` | `symbol_voting_key_status` (with `--account`) | no active key → fail. For the active key with the largest `remainingDays`: a successor key registered without a gap (`hasSuccessorKey` in `src/domain/voting.ts`, extracted from `buildVotingStatus` so that the tool's warning and the check use the same rule) → ok, `≤ RENEWAL_WINDOW_END_DAYS` (3; the end of the recommended renewal window; the same constant as the tool) → fail, `≤ warn-days` → warn, otherwise ok. skip without `--account` |
| 5 | `finality_participation` | `symbol_finality_participation`, `epochs: 1` (with `--account`) | participated → ok / missed → warn / no_active_key → fail / unavailable → warn. skip without `--account` |

- Each item is `{ id, status: ok|warn|fail|skip, detail, hint: string|null }`. **The hint is taken from the tool's output** (never write new advice text): 1 = the `checks[].hint` of the most severe check that is not ok (fail > warn > unknown; on a tie, the tool's fixed order), 2 = the "- " line of the summary, 3 = the note of a failed save (`NOT_SAVED_NOTE_PREFIX`) or the restart note (`RESTART_NOTE`), 4 = the entry of `warnings[]` that contains the 8-character prefix of that key (`warnings[0]` when there is no active key), 5 = `warning`, and `UNAVAILABLE_NOTE` for unavailable. The tool gives no warning more than 30 days ahead, so a warn with `--warn-days` > 30 can have a null hint.
- detail: 1 = the verdict and the id and status of each check that is not ok, and the detail of the most severe check (when healthy, the height difference from `chain` is added as the finalization lag), 2 = line 1 of the summary without the leading `version drift: `, 3 = the tool's summary, 4 = the key prefix, the remaining days, endEpoch and the estimated expiry (`successor registered` when there is a successor), 5 = the epoch and status, and the list of signed stages (`describeSignedStages`; e.g. `epoch 4027: participated (signed prevote and precommit)` / `missed (signed precommit, not prevote)`; for this, the tool is called with `format: 'detailed'`, so that it gets `stages` even when participated).
- Exceptions: `RestError` → fail (kind / status / path in the detail; the hint is from `describeError`). `ToolInputError` → fail (sentence 1 is the detail, the rest is the hint; an account that does not exist ends up here → exit 2). However, with `epochs: 1` and no proof, the tool throws instead of returning `unavailable`, so `ProofUnavailableError extends ToolInputError` was added (the message and the isError result on the MCP side do not change), and check makes only this exception a warn. Any other exception → fail (`describeError` writes the details to stderr). When 1 item fails, the rest still run.
- `account` in the JSON: the base32 address in the output of item 4. When item 4 failed or was skipped, the input masked with `maskIdentifier`; without `--account`, null. A 64-character hex (a value that may be a private key pasted by mistake) never appears in the output.

**exit code** (`decideExit`): 0 = everything ok or skip, 1 = some warn (no fail), 2 = some fail, 3 = could not run. It is 3 on an argument error, on a failure of `createAppContext` (`ConfigError` / `NetworkVerificationError` / a `RestError` of `/node/info`; stdout is empty), or when **every** item run (other than skip) was a `RestError` of `unreachable` / `timeout` / `redirect` (verdict `error`; a redirect counts as "not reaching the node at a usable URL"). With 3, stderr gets 1 to 2 lines with the cause and a hint. `process.exitCode` is used instead of `process.exit` (so as not to cut off what is still being written to stdout). A failed start of the server (exit 1) is as before.

**Output**: stdout only, no colour or decoration.
- text (default): line 1 `symbol check: OK|WARN|FAIL|ERROR (<host>, <network>, <time>)` (`<time>` is the local form of `ctx.instant(now)`, or utc when there is none), then 1 line for 1 item, `[ok] node_health: …`, and after a warn / fail line, 1 line `  hint: …` (not printed when the hint is null). `runCheck` makes the detail / hint 1 line (tabs and line breaks folded into spaces) and removes control and format characters (`printableItem`; json gives the same values; the last line of defence against strings that slipped past the tools' removal).
- json: the result of `runCheck` as it is, as 1 JSON document. `{ verdict: ok|warn|fail|error, exitCode, node: { host, network }, checkedAt: Instant, checks: [...], warnDays, account: string|null }`. The same conventions as structuredContent (numbers are numbers, Instant has its existing form). The shape is tested with `CheckReportSchema` (zod).
- `--quiet` prints nothing only on exit 0. Diagnostic lines (time limit, unreachable after start-up) go to stderr through `options.onDiagnostic`.
- **Only check mode writes to stdout**, and it writes in 1 place: the `process.stdout.write` that `index.ts` passes as `deps.stdout`. Server mode writes nothing to stdout, as before (the ban on `console.log` in §10 stays; so does biome's `noConsole`).

**Run-time limit**: `options.timeLimitMs` (default 120,000; no CLI flag is added). Each item races against the remaining time, and when the limit is reached, the running item and the rest become skip (with the reason in the detail). The overall result is **at least WARN (exit 1)**, printed even with `--quiet`, with the reason written to stderr. The requests of a cut-off item are not aborted, so the process can stay for up to about `SYMBOL_REQUEST_TIMEOUT_MS` (a cut-off `harvester_watch` may write its snapshot later, but the content is the same as a normal append).

**Outbound traffic and state**: only `SYMBOL_NODE_URL` and, through `symbol_version_drift`, `SYMBOL_REFERENCE_NODES` (`/node/info` only). No notification, no telemetry. As before, the only disk write is the state file of `symbol_harvester_watch` (§2-9; check appends 1 entry in 1 run).

**Location**: kept within `src/cli/` (`check.ts`, `format.ts`). So that the CLI can be split out into a separate package in the future, **`src/cli/` never imports `@modelcontextprotocol`** (checked by a test; an `import type` through `tools/_shared.ts` disappears at run time, so it is allowed for now). `src/cli.ts` is `runCli(argv, deps)` (`deps = { env, stdout, stderr, serve, version, now }`), and `index.ts` only wires the real process and sets `process.exitCode`. Do not change instructions / prompts / evals for the CLI (the CLI is outside MCP).

## 14. Distribution formats (npm / MCP Registry / .mcpb; .mcpb added in 0.8.0)

Users get it in 3 forms, and the content of all of them comes from the same tarball published to npm.

| Format | What builds it, and where | Who uses it |
|---|---|---|
| npm | the `publish` job of `release.yml` (Trusted Publishing, with provenance) | every MCP host configured with `npx -y symbol-mcp-server` |
| MCP Registry | `server.json` (the `registry` job of `release.yml` runs `mcp-publisher publish` with GitHub OIDC. When it fails, the failed job is re-run (for example, when npm did not show the new version yet) or a human publishes by hand ("When something fails" in `docs/RELEASING.md`). §8) | clients that look for servers in the Registry |
| .mcpb | built by the `github-release` job with `scripts/build-mcpb.sh` and attached to the GitHub Release | Claude Desktop (double-click, or Settings → Extensions) |

**How the .mcpb is made**: the official CLI `@anthropic-ai/mcpb` is not used, because its dependency (`tmp`) has a vulnerability with no fixed version. A `.mcpb` is "a plain zip with `manifest.json` at the top" (the CLI's `pack` also builds the same form with fflate's `zipSync`, and the signature is an optional appended block), and it is made with `zip -X -r`. The content is `manifest.json`, `icon.png` and `server/` (the tarball's `dist`, `package.json`, `README.md` and `LICENSE`, plus the production `node_modules` installed with `npm ci --omit=dev --ignore-scripts` from the lockfile of that release). The build fails unless the versions of the lockfile and `package.json` match. `unzip -Z1` checks that `manifest.json` is at the top, that `server/dist/index.js` and `@modelcontextprotocol/server` are there, and that no development dependency is there.

**manifest**: `mcpb/manifest.json` is the template (protected). `manifest_version` is "0.3" (the latest schema as of 2026-09; 0.4 only adds the `uv` type). `version` is a placeholder, "0.0.0", into which the build writes the release version. tools and prompts are not written in the template; the build declares them from `TOOLS` / `PROMPTS` of the bundled `dist/server.js` (`scripts/mcpb-manifest.mjs`; the description is sentence 1, and the `text` of a prompt is the template with `{account}` replaced by `${arguments.account}`). Adding a tool adds no manual work on the manifest. `server` is `node`, `args` is `${__dirname}/server/dist/index.js`, and `env` maps the 6 items of `user_config` to `SYMBOL_*` (only `node_url` is required).

**Unset values of user_config**: the reference implementation (`src/shared/config.ts` of mcpb) does not substitute an optional item that has neither a value nor a `default`, so the string `${user_config.x}` goes into the environment variable as it is. So every optional item gets a `default` (`""` for strings and directory, 10000 for `request_timeout_ms`). `src/config.ts` treats an empty or whitespace-only optional environment variable as unset (`test/unit/config.test.ts`). This rule, "optional items always have a default", is fixed by a test (`test/unit/mcpb-manifest.test.ts`).

**Node.js**: Claude Desktop ships with Node.js and runs node-type extensions on it (official). The official documentation does not say which version is bundled. `compatibility.runtimes.node` is ">=22", the same as `engines`, and no lower bound is written for `claude_desktop`, because no value can be confirmed officially. Verified facts (2026-09-23): a human installed the .mcpb in Claude Desktop on a real machine and confirmed that it works. There is no record of the Claude Desktop version at that time, or of the Node version in the log.

**Checking the origin**: the `.mcpb` gets a GitHub build provenance (`actions/attest`) and can be checked with `gh attestation verify <file>.mcpb --repo inotakeh/symbol-mcp-server`. It is not signed with `mcpb sign`, so Claude Desktop may show it as "unverified". State this in the README.

**Icon**: `mcpb/icon.png` (512×512) is an original shape that does not use the Symbol / NEM logos, and it can be regenerated with `scripts/make-icon.mjs` (no dependencies, only `node:zlib`).
